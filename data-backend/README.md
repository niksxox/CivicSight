# CivSight Data Backend

FastAPI + PostgreSQL/PostGIS backend for CivSight's data-engineering layer:
ETL, geospatial loading, infrastructure analytics, map feeds, and the
citizen-evidence AI handoff point.

## Requirements

- Python 3.11+
- PostgreSQL with PostGIS, or Docker Desktop
- `pip install -r requirements.txt`

## Environment

Copy `.env.example` to `.env` for local development. Do not commit `.env`.

Key variables:

- `DATABASE_URL`: SQLAlchemy URL for the API and ETL
- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_PORT`: Docker Compose database settings
- `API_PORT`: host port for FastAPI when using Docker Compose
- `NEARBY_RADIUS_METERS`: default project nearby-search radius
- `AI_CONFIDENCE_THRESHOLD`: citizen-evidence AI review cutoff

## Database Setup

Local PostgreSQL/PostGIS:

```bash
python scripts/init_db.py
```

Docker Compose:

```bash
docker compose up --build
```

The Compose stack starts PostGIS and the FastAPI app. PostgreSQL data is kept in
the `civsight_postgres_data` volume. On startup the API container automatically
runs `init_db.py` **and** `run_etl.py --reset`, so a single
`docker compose up --build` yields a fully populated, demo-ready database
(stale rows are cleared first — see Demo refresh below). The API is exposed at
`http://localhost:8000` by default and Swagger docs are at
`http://localhost:8000/docs`.

## Dataset Locations

Place raw inputs in `data/raw/`.

Current files inspected in this backend:

- `projects.csv`: synthetic/sample demo project data
- `facilities.csv`: synthetic/sample demo facility data
- `district_population.csv`: synthetic/sample district population and boundary WKT
- `network.csv`: synthetic/sample infrastructure lines
- `schools.csv`: synthetic/representative school infrastructure data
- `road (1).xml`: real PMGSY state-level aggregate data, non-spatial
- `water_connections (1).xml`: real Jal Jeevan Mission state-level aggregate data, non-spatial

Not currently available:

- Village/habitation-level PMGSY road geometry or coordinates
- Village/habitation-level JJM coordinates
- National LGD village CSV (`data/raw/lgd_villages.csv`)
- Real district boundary GeoJSON/shapefile; the current CSV uses demo WKT

## Dataset Status

Real:

- PMGSY aggregate state road counts/completed length (`road (1).xml`)
- Jal Jeevan Mission aggregate rural tap-water coverage (`water_connections (1).xml`)

Synthetic/representative:

- Schools (`schools.csv`), explicitly for prototype demonstration
- Demo projects, facilities, district population, and network CSVs generated by
  `scripts/generate_sample_data.py`

## Running ETL

Full demo refresh:

```bash
python scripts/init_db.py
python scripts/run_etl.py
```

Individual datasets:

```bash
python scripts/run_etl.py --dataset projects
python scripts/run_etl.py --dataset facilities
python scripts/run_etl.py --dataset population
python scripts/run_etl.py --dataset network
python scripts/run_etl.py --dataset schools
python scripts/run_etl.py --dataset roads
python scripts/run_etl.py --dataset water
python scripts/run_etl.py --dataset villages --chunk-size 50000
```

Each run logs the dataset, source file, rows read, valid, rejected, loaded, and
execution time. Rejected rows are written to `data/processed/rejected_<dataset>.csv`.

### Demo refresh (safe repeatability)

The default run is incremental: keyed tables (`projects`, `schools`,
`district_population`, `infrastructure_coverage`, `lgd_villages`) upsert, and
`facilities`/`infrastructure_network` use a deterministic `source_ref` upsert, so
re-running the same files never duplicates records.

For a clean slate before a presentation, pass `--reset`. This truncates the
target tables for the selected datasets (keeping already-loaded data safe when
a single dataset is refreshed) and then reloads:

```bash
python scripts/run_etl.py --reset
python scripts/run_etl.py --reset --dataset schools
```

## Geographic Precision

The ETL never invents coordinates.

- Source coordinates/geometries load into PostGIS with SRID 4326.
- PMGSY and JJM files currently available are state aggregates, so they load into
  `infrastructure_coverage` with `geo_precision =
  non_spatial_state_aggregate`.
- District centroids are not used as fake road or water locations.
- Real district boundaries should be supplied as WKT/GeoJSON/shapefile and
  normalized into `district_population.boundary` as `MULTIPOLYGON` EPSG:4326.

## LGD Villages

For national-scale LGD villages, place a CSV at `data/raw/lgd_villages.csv`
with columns equivalent to:

- `village_code`
- `village_name`
- `state`
- `district`
- optional `block`

The loader processes CSV chunks, defaults to 50,000 rows per chunk, validates
required fields, rejects duplicate village codes within a chunk, and upserts by
`village_code`.

## Synthetic Schools

The school dataset is synthetic/representative data for prototype demonstration.
It is deterministic and can be regenerated:

```bash
python scripts/generate_synthetic_schools.py --size 1000 --seed 42
```

It uses realistic school infrastructure fields and valid Andhra Pradesh demo
coordinates, but it is not official UDISE+ data and should not be described as
actual school records.

## Citizen Evidence AI Handoff

This backend stores citizen evidence and AI output but does not run the AI model.

Input:

- Existing `citizen_evidence` row
- Image-analysis result from the AI teammate

Expected AI output:

- `ai_condition`
- `ai_confidence`
- optional `ai_issue`

Destination:

- `citizen_evidence.ai_condition`
- `citizen_evidence.ai_issue`
- `citizen_evidence.ai_confidence`
- `citizen_evidence.needs_human_review`

Integration point (function):

- `app/services/evidence_handoff.py::apply_ai_evidence_result`

A thin HTTP endpoint is also exposed for the AI teammate to call directly:

- `POST /evidence/{evidence_id}/ai-result` with body
  `{"ai_condition": "...", "ai_confidence": 0.9, "ai_issue": "..."}`
  → persists `ai_condition`, `ai_issue`, `ai_confidence` and sets
  `needs_human_review = (ai_confidence < AI_CONFIDENCE_THRESHOLD)`.

## Geospatial Data Quality

Before loading, the pipeline audits every spatial frame (`etl/quality.py`):

- Point rows: lat/lng within India's bounding box (6–37.5°N, 68–97.5°E),
  non-null, no duplicate coordinates.
- Geometries: non-null, valid (shapely `is_valid`), correct SRID (4326), no
  duplicate geometries.

Problems are logged per dataset (`POINT QUALITY [...]` / `GEOMETRY QUALITY [...]`)
and, where possible, the offending rows are rejected with a reason rather than
silently loaded. All spatial columns carry GiST indexes (`idx_*_location`,
`idx_district_population_boundary`, `idx_network_geom`).

## Tests

Fast adapter/quality/transform tests (no database):

```bash
pytest tests/test_etl_adapters.py tests/test_etl_quality.py tests/test_etl_transform.py
```

Full suite (requires `httpx`, an installed test dependency) and a running
initialized PostGIS database. The session fixture seeds schema + ETL
automatically, then runs DB-backed tests (spatial queries, idempotency,
coverage, evidence handoff):

```bash
python scripts/init_db.py
python scripts/run_etl.py
pytest tests/
```
