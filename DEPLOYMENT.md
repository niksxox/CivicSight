# CivicSight — Deployment Guide

## Production architecture on Render

CivicSight is deployed as four Render web services plus managed Postgres and MongoDB Atlas:

| Service | Runtime | Purpose |
|---|---|---|
| `civicsight-frontend` | Docker + nginx | Static UI and reverse proxy |
| `node-api` | Docker + Express | Authentication, project CRUD, status workflow |
| `data-backend` | Docker + FastAPI | PostgreSQL/PostGIS analytics and infrastructure data |
| `ai-service` | Docker + FastAPI | AI/image analysis and Groq integration |
| `civicsight-postgres` | Render Postgres 16 | PostGIS infrastructure database |
| MongoDB Atlas | Managed MongoDB | Users and application/project data |

The frontend nginx service proxies `/api/*`, `/data-api/*`, and `/ai-api/*` to the other Render services over Render's private network. The browser therefore uses one CivicSight origin.

## Render deployment

The repository contains `render.yaml`. In Render:

1. Create a **Blueprint** from this repository and select `render.yaml`.
2. Use the `singapore` region for all services so private service networking works consistently.
3. When Render prompts for `sync: false` secrets, enter:
   - `MONGO_URI` on `node-api`
   - `GROQ_API_KEY` on `ai-service`
4. Render generates `JWT_SECRET` automatically.
5. Render creates the `civicsight-postgres` database and wires `DATABASE_URL` into `data-backend`.
6. The data backend runs `scripts/init_db.py` before deployment; the schema enables PostGIS.
7. Wait for all four services to report healthy.
8. Open the `civicsight-frontend` Render URL.

### Important secrets rule

Never commit `MONGO_URI`, `GROQ_API_KEY`, passwords, or other credentials to GitHub. Render environment variables are the production secret store.

If a credential has ever been pasted into chat, a terminal screenshot, an issue, or a public repository, revoke/rotate it before production deployment.

## Required Render variables

### node-api

- `NODE_ENV=production`
- `PORT=10000`
- `HOST=0.0.0.0`
- `MONGO_URI` — MongoDB Atlas connection string
- `JWT_SECRET` — generated by Render
- `CORS_ORIGIN` — automatically sourced from the frontend Render URL

### data-backend

- `PORT=10000`
- `HOST=0.0.0.0`
- `ENVIRONMENT=production`
- `DATABASE_URL` — automatically sourced from Render Postgres
- `NEARBY_RADIUS_METERS=1000`
- `AI_CONFIDENCE_THRESHOLD=0.65`

### ai-service

- `PORT=10000`
- `HOST=0.0.0.0`
- `ENVIRONMENT=production`
- `GROQ_API_KEY` — Groq API key
- `CORS_ORIGIN` — automatically sourced from the frontend Render URL

## Local Docker deployment

```bash
cp .env.example .env
docker compose up --build -d
docker compose exec data-backend python scripts/init_db.py
docker compose exec data-backend python scripts/run_etl.py
```

Local services use the ports documented in `docker-compose.yml`; Render uses port `10000` for each web service.

## Production notes

- The AI service uses the `1c-2g` Render plan because PyTorch/Transformers can exceed the 512 MB free-service memory limit.
- Free Render Postgres is suitable for a demo but expires after 30 days and has no backups. Upgrade it for durable production use.
- Free Render web services can spin down after inactivity; this is acceptable for a demo but not ideal for a public production system.
- The current ETL is intentionally not run automatically during every service startup. Run ETL as a controlled deployment/maintenance operation after the database schema exists.

## Troubleshooting

### Service says no open ports detected
Confirm the service is listening on `0.0.0.0:$PORT`. The Render Blueprint sets `PORT=10000`.

### Node API cannot authenticate
Check `MONGO_URI` and confirm the Atlas network access policy allows Render connections.

### Data API fails
Check the Render Postgres service, `DATABASE_URL`, and the data-backend deployment logs. The schema must successfully create the PostGIS extension.

### AI analysis fails
Check `GROQ_API_KEY` and the AI service logs. If the service is killed for memory/resource limits, increase its compute plan.
